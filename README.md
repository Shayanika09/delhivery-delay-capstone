# Delhivery Last-Mile Delay Intelligence Pipeline

Capstone for the AI/ML Certification Program (E&ICT Academy, IIT Roorkee). All data is synthetic, produced by `generate_data.py`.
One connected pipeline answers three questions: how long a parcel will take (Part B), which parcels will miss their promise (Part C), and which hubs need which playbook (Part D).

## How to run

From a fresh clone, in this order:

```bash
pip install -r requirements.txt
python generate_data.py          # prints 24 1224 48
python part_a_clean_eda.py
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py
python predict_delay.py
```

`models/delay_model.pkl` is regenerated by running `python package_model.py`. The committed pickle loads reliably only on the scikit-learn version pinned in `requirements.txt` (1.8.0); if your installed versions differ, re-run `package_model.py` instead of loading the committed pickle. Every script is deterministic: `predict_delay.py` run twice gives byte-identical `outputs/new_shipment_actions.csv`.

## Data findings

Source: `outputs/part_a_checks.csv`, `part_a_delay_by_group.csv`, `part_a_correlations.csv`. The 1,224 raw rows became 1,200 after removing 24 duplicates; 278 parcels (delay rate 0.2317) were delayed.

1. **Service type.** Express is delayed most often: 119 of 243 parcels, a delay rate of 0.4897 (Standard 0.2056, Economy 0.0857).
2. **Hub tier.** Delay rate climbs from 0.0400 for Tier 1 to 0.2150 for Tier 2 and 0.4400 for Tier 3.
3. **Distance.** Delay rate rises steeply with distance: 0.0219 (0-200 km), 0.1368 (201-400), 0.4364 (401-600) and 0.8523 (601+).
4. **Correlation with delivery_hours.** The three strongest columns are promised_hours (+0.8372), distance_km (+0.4013) and n_stops (+0.3247).
5. **Log transform.** declared_value_inr is right-skewed (mean 1533.05 versus median 1121.5), whereas after the log the mean (7.0277) and median (7.0224) nearly coincide, so the log makes the column roughly symmetric.

## Model results (regression)

Source: `part_b_metrics.csv`, `part_b_tree_depth.csv`, `part_b_gb_learning_rate.csv`, `part_b_cv.csv`. Split 840 / 180 / 180; the scaler is fitted on training rows only (train scaled max abs mean 0.0, test 0.2187).

- **Baseline.** Predicting the training mean gives validation R² of -0.0212: it explains none of the variation, and every real model must beat this.
- **Winner on validation.** Linear regression, RMSE 4.8912 hours (R² 0.9313). Gradient boosting is almost identical (RMSE 4.9165, R² 0.9306); random forest 5.5095 and the best decision tree 6.2796.
- **Bias versus variance.** The tree-depth table is best at depth 6 (val RMSE 6.2796). Depth 1 is high-bias: train 11.6334 and val 12.1324 are both high, with a gap of only 0.50. Depth 12 (gap 6.0) and unlimited depth (train 0.0, val 7.8368, gap 7.84) are high-variance: they memorise training rows and validation error rises again.
- **Learning rate.** 0.1 is best (val R² 0.9306). At 0.01 (R² 0.7127) the 100 trees move too slowly and underfit; at 1.0 (R² 0.8440) each step overshoots and the fit is unstable.
- **Cross-validation.** On the 1,020 training-plus-validation rows with one shared KFold, gradient boosting scores mean R² 0.9353 (std 0.0045) and linear regression 0.9261 (std 0.0048). The ranking disagrees with validation. The gap is small compared with the 180-row validation noise, so I would ship **gradient boosting**: its cross-validated score uses five times as many held-out rows and is the more reliable estimate, and trees can capture the interaction effects (sale x Express, long distance x rain) that a linear model cannot. The pipeline's final test score (linear regression, one use of the test rows) was R² 0.9493, RMSE 4.5235.

## Model results (classification)

Source: `part_c_*.csv`. Stratified split 840 / 180 / 180 with 195 / 42 / 41 delayed parcels.

- **Blind baseline.** Predicting "on time" for everything has validation accuracy 0.7667 but recall 0: it catches no delayed parcel, so it is useless for the operations task despite looking accurate.
- **Models.** Logistic regression F1 0.8046, decision tree depth 6 F1 0.747, default forest F1 0.7848; all have accuracy 0.8833 to 0.9056, above the blind baseline.
- **Noise columns.** The five bookkeeping columns hold a combined 0.2245 of the forest's importance across 17 columns (a random forest spreads importance over noise), yet all five rank 8th or lower by F-score (ranks 8, 12, 14, 16, 17) with F-scores at most 4.5847. So they are outside the top 7: the seven that remain are distance_km, hub_tier, hub_daily_capacity, n_stops, promised_hours, rain_flag and sale_event_flag.
- **SelectKBest table.** Validation F1 is 0.6988 (k=5), 0.8333 (k=7), 0.7857 (k=10), 0.8049 (k=12) and 0.7848 (k=17): k=7 is best, k=5 drops real signal, and k=17 includes noise.
- **Tuning.** Grid search (best CV accuracy 0.8952, val F1 0.775) and randomized search (0.8905, val F1 0.7848) did **not** beat the untuned forest on the same 7 features (val F1 0.8333). With only 42 delayed validation rows, a one-parcel change moves F1 by roughly 0.01 to 0.02, so these differences are mostly noise and the tuning gains are not trustworthy. The final model is therefore the default forest on the 7 selected features.
- **Threshold.** Validation recall is at least 0.80 up to t = 0.5 (precision 0.7955, recall 0.8333, 7 missed parcels, 9 false alarms); at 0.6 recall drops to 0.7619. The highest threshold meeting the rule is **0.5**.
- **Test result.** At 0.5: precision 0.6889, recall 0.7561, F1 0.7209 (TP 31, FN 10, FP 14). Test recall is lower than validation recall (0.8333); with only 41 delayed parcels, one parcel is about 2.4 recall points, so the validation estimate was somewhat optimistic and the true recall is likely around 0.75.

## Operations recommendation

- **Escalate hubs (9), delay rate in brackets:** HUB13 Nagpur (0.46), HUB15 Kochi (0.36), HUB17 Patna (0.46), HUB18 Ranchi (0.38), HUB19 Guwahati (0.62), HUB20 Raipur (0.48), HUB21 Bhubaneswar (0.40), HUB23 Siliguri (0.44), HUB24 Agartala (0.54). The segment's mean delay rate is 0.46, versus 0.155 for Watch and 0.0257 for Standard (`segment_profile.csv`).
- **Tier label mismatches** (`tier_vs_segment_mismatch.csv`): HUB07 Kolkata (Tier 1, behaves as Watch), HUB13 Nagpur (Tier 2, behaves as Escalate), HUB15 Kochi (Tier 2, behaves as Escalate), HUB22 Dehradun (Tier 3, behaves as Watch). The tier label should therefore not drive playbooks on its own; use the data-driven segment.
- **Alert threshold 0.5.** From `part_c_final_test.csv`: about 7 of every 10 flagged parcels are really delayed (precision 0.6889), and about 7.5 of every 10 delayed parcels are caught (recall 0.7561).
- **New parcels.** Of the 48 new parcels, 8 were flagged and 6 of them need escalation to a hub manager (the other 2 get a proactive customer call) (`new_shipment_actions.csv`).
- **Why K = 3.** The across-to-within ratio is 2.894 (K=2), 5.3928 (K=3), 6.3047 (K=4) and 6.8866 (K=5), and it keeps rising with K simply because more clusters always tighten the groups. But K=4 gives cluster sizes 8-7-5-4 and K=5 gives 8-7-4-3-2, each with a cluster of fewer than 6 hubs, too small to carry its own playbook. K=3 (9-8-7) gives three well-separated segments that match the three playbooks operations runs.

## Production plan

**(a) Production-readiness characteristics mapped to the repository**

| Characteristic | Item in this repository |
| --- | --- |
| Accuracy | Validation/test metrics in `part_c_models.csv`, `part_c_final_test.csv`; recall-driven threshold in `part_c_thresholds.csv` |
| Reliability | Median imputation, sentinel handling and Unknown payment mode in `clean_shipments`; no missing values reach the model |
| Reproducibility | `random_state=42` everywhere, pinned `requirements.txt`, deterministic `generate_data.py`, `package_model.py` regenerates the pickle |
| Performance (speed) | A 7-feature random forest scores 48 parcels in well under a second in `predict_delay.py` |
| Maintainability | Shared code in `src/shipment_prep.py`; one script per part; saved config in `part_c_final_config.csv` |
| Consistency | `predict_delay.py` imports `clean_shipments`/`build_features` and uses stored medians and `feature_order.csv`, so training and prediction preprocess identically |
| Monitorability | `part_d_reload_check.csv` and the quantities below |

**(b) Quantities to monitor, with triggers**

- Weekly delayed share of delivered parcels: trigger if it moves more than 5 points from the 0.2317 training rate for two weeks in a row.
- Weekly share of parcels flagged: trigger if it leaves a band of 0.15 to 0.30 (the flag rate on validation at t=0.5 is 0.2444).
- Recall on parcels whose outcome is now known: trigger if it falls below 0.65 on at least 40 delayed parcels (test recall was 0.7561).

**(c) Retraining and the sale window.** Retrain monthly, and immediately if a monitor trigger fires, always keeping a time-ordered holdout of the latest weeks. The 15-28 September sale window (`sale_event_flag`) must be compared with the same kind of event (last sale, or a pre-sale forecast), never with ordinary weeks, because it adds delay by design. Data drift here would look like a shift in lane distance or stops per route, a changed service mix (more Express), new hubs, or rising delay rates inside one segment while the others stay flat.

## Limitations

1. The data is synthetic, generated from a known formula, so real-world performance will be lower and noisier than reported here.
2. The test set has only 41 delayed parcels, so test precision/recall have wide uncertainty (one parcel is about 2.4 recall points).
3. The threshold of 0.5 and the final configuration were tuned on a single 180-row validation split, so they may not be stable.
4. Hub segments use only 24 hubs and 50 shipments each, so one hub can change a segment profile; K=3 is imposed by the business, not discovered.
5. The hub-manager escalation rule uses historical segments and does not adapt to short-term conditions such as weather.
